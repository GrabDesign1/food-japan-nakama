## 1. 何を作るか

Food Japan Summit（2026年11月 宮崎／12月 名古屋）の参加者を会員とし、イベントで生まれた出会いを商談・共創事業まで追跡するWebシステム。

イベント当日で終わらせないことが目的なので、**イベント管理システムではなく、通年で動く共創CRM**として設計する。

### 差別化の中心

一般的なビジネスマッチングは「企業を探す」構造だが、本システムは**「動かせるモノ・場所・条件を探す」構造**にする。

具体的には、余っている食材／探している原料／加工できる設備／販売できる地域／実証可能な店舗／物流上の困りごと／地域が解決したい課題 を、企業プロフィールの自由記述ではなく**1件ずつのレコード（持ち寄り台帳）**として持つ。検索とマッチングはすべてこの台帳を見る。

ここが崩れると、ただのマッチングサイトになる。

### 主要なマッチングの型（4つ）

| ID | 組み合わせ | 主な論点 |
|----|-----------|---------|
| a1 | 生産者 → 流通・小売 | 出荷先と数量を先に決める。規格外・小ロットの引き取り |
| a2 | 生産者 → 食品メーカー | 余っている食材と加工設備を突き合わせる |
| a3 | 生産者 → 飲食・ホテル | 産地表示と少量配送 |
| a4 | 食品メーカー → 飲食・ホテル | 試作を実店舗で出して反応を見る |

検索画面はまずこの4つのどれかを選ばせ、そこから条件を絞る。

## 2. 未決事項（実装前に決める）

**ここが埋まらないと設計が確定しません。** 優先度順。

### 2-1. 会員種別ごとの入力項目マトリクス【最優先】

生産者に「加工設備」を、飲食店に「作付面積」を聞いても答えられない。プロトタイプでは種別セレクトを用意したが、**中身の出し分けは未実装**。

必要な作業：6大分類×細分類ごとに、必須項目・任意項目・非表示項目を一覧化する。

これはシステム側で決められない。実際の参加企業の顔ぶれを見て決める必要がある。2025年の参加者187名の業種内訳（食品メーカー39／農業31／食品加工23／マーケティング21／行政21／酒造12／水産10／飲食・ホテル9／流通卸・小売7／大学3／通信3／その他12）が参考になる。

### 2-2. 持ち寄り台帳の「数量」書式【最優先】

現状のサンプルは `年12t` `月20ケース` `2〜3店` `1名` と混在している。このままだと「年3t以上の原料」という検索が成立しない。

選択肢：

- **A案**：数値＋単位を分けて持つ（`amount: 12, unit: "t", period: "year"`）。検索は効くが、生産者に単位を選ばせる入力は面倒で登録率が落ちる。
- **B案**：自由記述のまま。登録は楽だが範囲検索を諦める。
- **C案**：主要カテゴリ（食材・原料）のみA案、他はB案。

**推奨はC案**。食材・原料が検索の8割を占めるはずなので、そこだけ構造化すれば足りる。ただし実データを見るまで断言できない。

### 2-3. タグのマスタ設計

プロトタイプの「出せるもの」20個・「探しているもの」18個は仮置き。運用開始後にどう増減するか不明。

決めること：タグを固定マスタにするか、会員が自由に追加できるようにするか。自由追加にすると表記ゆれ（「規格外」「規格外品」「B品」）で検索が死ぬ。**固定マスタ＋事務局が追加申請を承認する形を推奨**。

### 2-4. 台帳の分類9つが妥当か

食材・原料／加工設備／技術・ノウハウ／販路・売り場／実証の場／物流／資金・補助／人材／地域課題。これも仮置き。

特に、支援系会員（採用・SaaS・マーケティング・大学）は「食材・原料」が空になる。「人材」「技術・ノウハウ」で吸収しているが、支援系が増えるなら別建てが要る。

### 2-5. 自治体・JA・大学の支払い方法

企画書のターゲットに自治体30団体が含まれる。この層はカード決済ができず、年度予算＋請求書払いになる。

決めること：銀行振込を金額に関係なく受けるか、エンタープライズのみにするか。振込を受けるなら、Stripeの外で請求書を発行し、入金確認して手動でプランを付与するフローが要る（第9章参照）。

### 2-6. 生産者の細分類

現状：野菜・青果／生花／お茶／酪農・乳業／水産。

**畜産・米穀・果樹が入っていない**。宮崎牛（畜産）、酒米（米穀）は企画書に登場するため、追加の要否を確認すること。

### 2-7. 保守体制

イベントは年2回でもシステムは365日動く。誰が障害対応するかを実装前に決める。

2階層。1階層だと選択肢が20以上並んで使いにくい。

|--------|--------|
| 生産者 | 野菜・青果／生花／お茶／酪農・乳業／水産 ＋（畜産・米穀・果樹を要検討：2-6） |

| 支援・その他 | 物流／採用／大学／研究機関／マーケティング／SaaSサービス |

### 担当者の立場（会員種別とは別の軸）

バイヤー／シェフ・料理人／生産者／一般（その他の担当者）

**会員種別とは独立して持つ**。同じ「流通・小売」でもバイヤーと物流担当では話が通じないため。検索の絞り込み条件にもする。ユーザー単位の属性なので `users.stance` に置く。

## 6. 商談フェーズ

```
0. 出会う          興味の送受信のみ。まだ話していない
1. 初回商談        一度会った・話した
2. 条件整理        数量・価格・時期を詰めている
3. 試作・PoC       サンプルや試験を回している

5. 成約・商品化    継続的な取引になった
```

### 停滞判定

`last_activity_at` から30日経過で `is_stale = true`。表では期限欄が赤字、ボードではカード左端が赤線。

**宮崎（11月）と名古屋（12月）の間の1か月が最も止まりやすい**ため、この期間は事務局からのリマインドを別途検討する。

## 8. 検索仕様

### 絞り込み条件

1. 組み方（a1〜a4／未選択）
2. 探しているもの（台帳カテゴリ9種）
3. 会員種別（大分類）
4. 相手の立場（4種）
5. 地域（7区分）
6. キーワード（会員名・紹介文・タグ）

### 表示順

記入率（レベル）が高い会員を上位に。「入力するほど探されやすくなる」構造にして、プロフィール記入を促す。

### 実装

会員数が数千規模なら PostgreSQL の全文検索（`pg_trgm` ＋ GIN）で足りる。数万を超える、またはタグの組み合わせ検索が重くなったら Typesense か OpenSearch を検討。**最初から入れる必要はない。**

## 9. 課金・Stripe連携

### プラン構成

| プラン | 月額（税別） | 主な上限 |
|--------|------------|---------|
| フリー | ¥0 | 台帳5件／案件1件／興味送信 月1件 |
| スタンダード | ¥15,000 | 台帳無制限／案件3件／興味送信 月10件／ユーザー3名 |
| プロ | ¥30,000 | 案件10件／興味送信 月30件／ユーザー10名／優先マッチング／分析 |
| エンタープライズ | 個別 | 無制限／SSO／監査ログ／専任担当／年額・振込可 |

都度課金：興味送信チケット10枚 ¥8,000／案件の追加掲載 ¥5,000／出展ブース ¥200,000／追加ユーザー ¥3,000月

※この価格は仮置き。企画書の協賛プラン（15〜400万円）と年間会員（月3万円）との整合は未調整。**協賛と本システムの課金をどう関係づけるか要決定。**

### Stripeの使い方

- **Stripe Checkout** に遷移させる。カード情報を自社で受け取らないため、PCI DSSの対応範囲がほぼゼロになる。
- **Stripe Customer Portal** をプラン変更・カード変更・解約の画面として使う。自作しない。
- 自社DBには `stripe_customer_id` と `stripe_subscription_id` のみ保持。
- **権限判定は自社DB側で行う**。「スタンダードだから興味送信は月10件まで」の判定でStripeに毎回問い合わせると、Stripe障害時にサービスが止まる。

### 受けるWebhook（最低限）

```
checkout.session.completed        契約開始 → subscriptions を作成
customer.subscription.updated     プラン変更 → plan_id を更新
customer.subscription.deleted     解約 → status を canceled に
invoice.payment_failed            決済失敗 → 事務局に通知、3回で停止
invoice.paid                      支払完了 → invoices に記録
```

Webhookは冪等に。同じイベントが複数回届く前提で `stripe_event_id` を保存して重複を弾く。

### 銀行振込

Stripeの外になる。自治体・JA・大学はカード決済ができないため（2-5）、以下のフローが要る。

1. 事務局が請求書を発行（Stripeの請求書機能または外部）
2. 入金を確認
3. 事務局が手動で `subscriptions` を作成／延長

**このフローを作らないと、企画書の「自治体30団体」目標が課金面で成立しない。**

### インボイス制度

適格請求書には登録番号の記載が必要。Stripeの請求書テンプレートに事務局の登録番号を設定すること。忘れやすい。

1. **認証・テナント・権限** — 後から入れると全画面を直すことになる
2. **会員プロフィール＋審査フロー** — 事務局が最初に使う

5. **興味送信・メッセージ**

7. **共創プロジェクト**
8. **課金・Stripe**

課金を後にするのは、無料で使ってもらって使われ方を見てから価格を確定したほうが失敗しないため。ただしイベント（11月）に間に合わせる必要があるなら、1〜6までを先に出す判断もあり得る。

## 12. 注意点

### AUBAとの関係

本システムはAUBA（eiicon運営）の機能構成を参考にしているが、**画面デザインの模倣はしない**。機能が同等でも見た目は独自に作る。

AUBAの掲載情報を転用してはならない。AUBAは利用規約で、掲載情報をAUBA上でのオープンイノベーション目的のメッセージ送信以外に使うことを禁じている。会員データは自前で集めること。

### 個人情報

会員は法人だが、担当者名・メールアドレス・電話番号は個人情報。プライバシーポリシーと、退会時のデータ削除フローを用意する。

商談メモには相手企業の非公開情報（原価・仕入価格・生産量）が入る。**メモは所有者の会員のみが読める**設計にすること。相手企業には見せない。

### メッセージの営業利用

イベント参加者リストを狙った営業目的の一斉送信が必ず発生する。チケット制はその抑止も兼ねている。通報機能と、事務局が停止できるフローを用意する。

## 13. プロトタイプの読み方

`food-japan-connect-v5.html` をブラウザで開くと全画面が動く。

- 右上「デモ切替」で会員／事務局を切り替えられる。**実装時にこのボタンは不要**
- 企業名・数値・請求データはすべて架空
- localStorage等は使っていない。リロードで初期状態に戻る
- データは全て `<script>` 内の配列（`COS` `LEDGER` `DEALS` `PLANS` など）。ここを見れば必要なフィールドが分かる
